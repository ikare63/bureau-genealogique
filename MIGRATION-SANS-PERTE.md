SessionStorage : jeton du moteur et expiration (60 minutes maximum), anciens jetons retirés à la saisie/expiration/oubli. Ne pas joindre de jeton au secours ni le copier dans un rapport. Le CMS possède aussi un jeton en mémoire pour ses fonctions de publication : ne pas l’utiliser pour migrer les sauvegardes. Le CMS refuse désormais d’écrire dans le dépôt `data` par son ancien chemin.

Cache Storage/service workers : les ressources de l’application peuvent rester sur une ancienne version, particulièrement Culina. Ne pas vider le site pour forcer une mise à jour : cela pourrait supprimer les données. Les caches ne remplacent jamais une sauvegarde personnelle. Les URL externes, photographies ou PDF qui n’existent que sur un service distant ne sont pas nécessairement contenus dans les JSON. Les fichiers déjà téléchargés dans Android/Fichiers doivent aussi être copiés.

Cet inventaire vient des sources disponibles, pas d’une inspection de l’appareil. Des clés historiques ou applications supplémentaires peuvent exister. **L’inventaire réellement présent et l’export des coffres/historiques restent des conditions bloquantes.**

## Limites de taille, authentification et fermeture

Lecture GitHub authentifiée : au-delà de 1 Mo, métadonnées `object` puis contenu brut du blob épinglé au SHA, sans URL publique. Fixture UTF-8 réellement supérieure à 1 Mio testée. GitHub Contents accepte les médias object/raw entre 1 et 100 Mo ; au-delà de 100 Mo, cette API n’est pas utilisable. Le moteur limite volontairement les écritures à **90 Mio de JSON sérialisé** et ne découpe pas les grosses pièces. Le base64 augmente la taille et la mémoire consommée. Un Scriptoria au-delà de cette limite nécessite une autre stratégie avant migration (données et pièces séparées privées, manifeste/hachage et restauration dédiée à tester) : ne pas tronquer les fichiers. La mémoire/quota d’Android et les volumes réels n’ont pas été éprouvés.

Les jetons ne sont jamais mis en URL ni dans le dépôt ; destination API restreinte au dépôt privé, détection des champs secrets avant transfert, jeton de session avec expiration et bouton d’oubli. Un script malveillant de la même origine peut néanmoins accéder au jeton en sessionStorage : ce stockage n’est pas un coffre isolé. Utiliser ensuite un jeton finement limité à `data`, à durée courte. Aucune installation ni serveur personnel ne sont nécessaires pour une opération manuelle de taille compatible ; un site statique ne peut garder un secret de serveur. Ne pas publier un jeton dans GitHub Pages.

Après fermeture normale, les données IndexedDB/localStorage doivent persister, sous réserve de quota/éviction/réglages du navigateur ; le jeton peut devoir être ressaisi. Une restauration de session peut conserver sessionStorage jusqu’à expiration. Aucune synchronisation ne s’exécute navigateur fermé. Les comparaisons périodiques ne sont pas réactivées automatiquement après réouverture. Refaire une comparaison ; une dernière réussite historique ne prouve pas la fraîcheur actuelle.
